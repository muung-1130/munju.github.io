## 3. EKS GitOps 운영 (ArgoCD) 및 Argo Rollouts Blue/Green 실전환

### GitOps 운영 체계
- Frontend·Backend·AI를 별도 Argo CD Application/Namespace로 분리 — 장애 영향 범위 축소.
- Kustomize overlay로 환경별 리소스·ECR Digest 관리.
- Argo CD 자동 Sync에 `prune=false`, `selfHeal=false`, `allowEmpty=false` 안전 정책.
- HPA/KEDA replica 값과 Git 선언값 차이를 `ignoreDifferences`로 분리 처리(정상 오토스케일링 drift ≠ 장애).
- **AppProject가 project-scoped repo credential을 요구한다는 함정 발견·해결**(2026-08-11): 새 AppProject를 만들면 기존 저장소 SSH Secret이 `project` 필드로 스코프돼 있어 조용히 실패(`SSH agent requested but SSH_AUTH_SOCK not-specified`라는 오해하기 쉬운 에러). Secret을 복제해 `project` 필드만 바꿔 해결 — 이후 재발 방지 체크리스트화.

### Argo Rollouts 실운영 전환 (2026-08-21 ~ 08-22) — 대표 성과
`dairun.site`(실 프로덕션 프론트엔드)를 평범한 Deployment에서 **Argo Rollouts blueGreen Rollout**으로 실제 전환하고 Blue/Green 데모 영상까지 촬영한 프로젝트. 다음은 이 과정에서 실제로 겪고 해결한 사고들(인터뷰용 트러블슈팅 사례로 유용):

1. **~8분 실제 아웃티지 발생 및 원인 분석**: 사용자의 구두 확인("머지 눌렀어")만 믿고 기존 Deployment를 0으로 스케일했으나 실제로는 MR이 병합되지 않은 상태였음. `git log origin/main`으로 직접 검증하지 않은 것이 원인. 이후 "스케일 0 → 즉시 병합 클릭 → 즉시 하드 리프레시"를 백투백으로 실행하는 절차로 재발 방지.
2. **AppProject/Application CR 자체는 GitOps로 자기 자신을 동기화하지 않는다는 함정**: `ignoreDifferences`를 Deployment 기준에서 Rollout 기준으로 바꾸는 MR이 병합돼도 라이브 Application 객체엔 반영 안 됨 → `dai-run-prod-frontend`가 계속 `OutOfSync`로 표시. `kubectl patch application ... --type merge`로 직접 수정 후 `refresh=hard`로 해결.
3. **오진단으로 인한 2차 사고**: 개발자가 색상 변경 MR을 올렸으나 `autoPromotionEnabled: false`라 Preview 상태로 대기 중이었는데, 이를 "Rollout 전환이 문제"라고 오판해 원본 전환 MR(!37)을 Revert — ArgoCD가 자동 적용하며 삭제됐던 Deployment가 되살아나 **Deployment와 Rollout이 동일 selector로 동시에 존재**하는 상태 발생(7 pod, 정상 3-4개 대비 초과). `git revert <revert-commit>`으로 재복구.
4. **실측으로 "무중단"이 아님을 확인하고 문서 정정**: Blue/Green Promote 순간 실제 몇 초간 503 발생을 `kubectl get events`로 확인(Istio Ambient mesh의 ztunnel 전파 지연 추정). 기존 데모 문서의 "무중단" 서술을 정확한 표현으로 수정.
5. **stg/main 드리프트 근본 해결**: Rollout 전환 이후 `stg` 브랜치가 삭제된 파일을 계속 참조해 배포 MR이 영구 충돌 → `git merge origin/main`으로 재정렬, rename 감지로 자동 해결, 걸려있던 백엔드 배포 2건도 부수적으로 해소.
6. **두 번째 사람 승인 게이트까지 제거**: GitOps 배포 MR 자동 병합 구현(위 2절 참고) — 애플리케이션 코드 MR 병합 하나만 사람이 클릭하면 프로덕션까지 자동 반영되는 파이프라인 완성, 실제 배포(course 페이지 배경색 변경)로 end-to-end 검증.

**최종 확인 상태**: `rollout.argoproj.io/dir-frontend`가 `dir-frontend-ns`에서 `Healthy`, 기존 Deployment 삭제됨, HPA가 Rollout을 정상 참조, `https://dairun.site/`가 안정적으로 HTTP 200 응답.

### Argo Rollouts Dashboard 검증 (2026-08-21)
- `dir-argo-rollouts-ns`에 readonly 모드로 배포·정상 동작 확인(SSH 포트포워딩으로 접근 검증).
- 클러스터 유일의 실제 `Rollout` 객체(`dairun-application-rollout-smoke`, `dir-gitops-test-ns`)를 데모/테스트용 fixture로 활용하는 절차 수립.

## 4. DevSecOps 보안 검사 체계

- **SonarQube**: 소스 코드 품질·보안 이슈 분석, GitLab 파이프라인 연계.
- **Trivy CRITICAL gate**: ECR Push 전 컨테이너 이미지 검사(2절 참고).
- **Amazon ECR Enhanced Scanning + Inspector** 구성 확인: `dai-run/*`(실 앱 서비스, ~22개 저장소) `SCAN_ON_PUSH`, `dairun/*`(인프라/벤더 이미지 미러) `CONTINUOUS_SCAN`. **실측으로 발견한 보안 공백 3가지**(2026-08-18):
  1. GitLab 파이프라인에 배포 차단용 스캔 게이트가 전혀 없었음(Inspector는 탐지만, 배포는 안 막음) → 이후 SonarQube+Trivy 필수 게이트 구현.
  2. 스캔 주기가 거꾸로 설계돼 있었음 — 실제 배포되는 앱 이미지가 1회성 스캔, 인프라 미러가 오히려 지속 스캔.
  3. OWASP ZAP은 ECR에 이미지만 있고 **CronJob이 클러스터에 전혀 없어** 한 번도 실행된 적 없음(태그명은 "weekly"였지만 실제 스케줄 없음) — `kubectl get cronjob -A`로 직접 확인.
- **ECR KMS 암호화 + Immutable Tag** 정책 적용, digest 기반 배포.
- **OWASP ZAP Baseline DAST**를 비운영 EKS Service 대상 report-only로 실행: 내부 URL 3개 Spider/Passive Scan, Critical/High 0건, Medium 4/Low 12/Informational 3건 기준선 확보. ZAP 실행 ServiceAccount 토큰 비활성화, non-root, seccomp RuntimeDefault, capability 제거, 최소 egress NetworkPolicy 적용. 검사 후 대상 Application `Synced/Healthy`, Deployment `2/2 Ready` 유지 확인.
- **배포 차단 보안 게이트 실제 구현**(2026-08-18, 브랜치 `review/security-gates-20260818`): 단위테스트 → SonarQube Quality Gate(`allow_failure: false`, 최대 600초 대기) → 이미지 빌드 → Trivy → ECR Push → GitOps 갱신 → Argo CD 배포 순서로 하드 게이트화.

## 6. Kafka → SNS/SQS/KEDA 메시징 전환 (AI/Backend)

- **근본 원인 분석**: Kafka DNS·브로커 불안정으로 Consumer가 연쇄 종료, Argo CD가 Degraded — 로그·이벤트 기반으로 원인 규명.
- **SNS MessageAttributes + 구독 Filter Policy**로 이벤트를 서비스별 SQS Queue에 분배.
- Consumer에 **SQS Long Polling, 성공 후 Delete, 오류 시 재처리** 흐름 구현 + 단위 테스트 추가.

## 7. AWS Site-to-Site VPN 구축 (strongSwan) — Codex CLI 세션 기록

> 이 항목은 Claude Code가 아니라 같은 `/srv/cicd-admin`에서 병행 사용한 **Codex CLI**(`~/.codex/sessions/2026/08/10~16/`) 세션에 기록되어 있었습니다.

### 역할 선언 (2026-08-11)
> "이 설계도 기준으로 aws 마이그레이션을 진행할 예정이고. 나는 cicd 담당자이며 site to site VPN 구축을 담당하고 있어."

### 확정 아키텍처
```
온프레미스 (192.168.0.0/24)
  → strongSwan Linux (IKEv2 + PSK + NAT-T, 터널 2개)
  → AWS Site-to-Site VPN
  → Virtual Private Gateway
  → AWS Main VPC (10.10.0.0/16)

Main VPC ←(VPC Peering)→ CI/CD VPC   (VPN과는 별개 경로, 전이 라우팅 불가라 온프레미스는 CI/CD VPC에 접근하지 않는 것으로 확정)
```
- Transit Gateway 대신 **VGW + 정적 라우팅**으로 단순화 결정(CI/CD VPC까지 온프레미스에서 접근할 필요가 없다고 스코프를 좁혔기 때문).
- Phase 1/2 권장 암호화: AES256 / SHA2-256 / DH Group 14 (`aes256-sha256-modp2048`).

### 구축 순서 (실제 진행)
1. 온프레미스 CIDR(`192.168.0.0/24`)·공인 IP(`<온프레미스 공인 IP, 비공개>`) 확인 — 학원(교육기관) 네트워크라 공유기 관리자 권한이 없어 NAT 뒤에 있음을 직접 진단(`ip route`, `curl checkip.amazonaws.com`, `tracert` 등으로 Windows/Linux 양쪽에서 교차 검증).
2. 관리자 권한 없이도 가능한 범위로 **PoC 스코프를 `/32`(strongSwan 서버 한 대)로 축소**하는 전략적 판단 — 공유기 정적 경로 없이도 strongSwan 서버 자신의 트래픽만으로 AWS 연결을 검증할 수 있음을 확인.
3. AWS 측 리소스 설계: Customer Gateway → VGW 생성 및 Main VPC 연결 → Site-to-Site VPN Connection(정적 라우팅) → Tunnel 1·2 설정 다운로드.
4. strongSwan 사전 준비: 기존 IPsec 프로그램 충돌 확인, 네트워크·방화벽 상태 백업, `charon-systemd + strongswan-swanctl`(legacy `ipsec.conf` 방식 대신 `swanctl` 방식 채택) 설치.
5. VPN 전용 VM 별도 구축(2vCPU/2~4GB, 브리지 네트워크 — VirtualBox NAT는 이중 NAT가 되어 회피) 및 사양 산정.
6. Tailscale(WireGuard 기반)과 비교 검토 후 **"AWS 공식 Site-to-Site VPN 구축 증빙이 필요하다"는 프로젝트 목적에 맞춰 strongSwan 선택** 확정.

### 실제 배치 확인 (2026-08-16)
strongSwan은 최종적으로 **`192.168.0.214`** — 온프레미스 VPN 게이트웨이 전용 서버 — 에 설치되어 있음을 실제 클러스터 조사로 확인:
```
온프레미스 서버·Kubernetes
→ 192.168.0.214 strongSwan
→ IPsec Site-to-Site VPN
→ AWS Virtual Private Gateway
→ dir-main-vpc
→ EKS 및 AWS 내부 서비스
```
