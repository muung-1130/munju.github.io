01 / 지역 조회 최적화

대표 개인 기여 · 저장된 실습 결과
QUERY BLOCK / BEFORE40.637ms단일 실습 · 기존 측정 단계
QUERY BLOCK / AFTER0.413ms단일 실습 · 파티셔닝 + 지역 코드 조건
OBSERVED REDUCTION약 99.0%단일 실습 · 저장된 실행 시간 감소율

단일 실습 측정값입니다. 운영 서비스 응답 시간이 아니며, 전후 스키마·쿼리 조건·캐시를 동일하게 통제한 반복 벤치마크가 아닙니다. 감소 전체를 파티셔닝 단독 효과로 단정하지 않습니다.

01

문제 — 특정 지역을 찾아도 캠핑장부터 전체 스캔

기존 계획은 CAMP_SPOT을 먼저 읽고 위치 정보를 확인했습니다. JSON 캡처에서 선행 노드의 실제 행 수는 5,512행, 쿼리 블록 실행 시간은 40.63673494ms였습니다. 관련 없는 지역을 읽는 범위를 줄이는 구조를 검토했습니다.

02

적용 — CAMP_LOCATION에 LIST(region_code)

위치 조건과 직접 연결되는 테이블을 대상으로 17개 시도와 미분류 코드 0을 포함한 18개 파티션을 정의했습니다. 적재 코드에서 신·구 지역명을 지역 코드로 매핑하고 조회에 region_code = 3을 명시했습니다.

03

검증 — p_daegu 선택과 조인 순서 확인

실행계획에서 p_daegu만 선택하고 위치 데이터 57행을 먼저 읽은 뒤, CAMP_SPOT을 eq_ref / PRIMARY로 조회하는 흐름을 확인했습니다. 실행 시간은 EXPLAIN 결과가 아니라 별도의 ANALYZE FORMAT=JSON 캡처를 근거로 했습니다.

EXPLAIN PARTITIONS
SELECT s.camp_name
FROM CAMP_SPOT AS s
JOIN CAMP_LOCATION AS l ON s.camp_id = l.camp_id
WHERE l.region_code = 3
  AND l.province = '대구광역시';
지표기존 측정 단계파티셔닝 + 지역 코드 조건
쿼리 블록 시간40.63673494ms0.4125489ms
선행 테이블CAMP_SPOTCAMP_LOCATION
선행 노드 실제 행 수5,512행57행
위치 파티션비파티션 비교본p_daegu
이후 캠핑장 접근—eq_ref / PRIMARY

단일 실습 측정. 5,512행과 57행은 서로 다른 선행 접근 테이블의 값이며, 같은 테이블의 전체 I/O 감소율로 계산하지 않습니다.

설계 비용도 함께 고려했습니다. 파티션 버전의 위치 테이블은 PRIMARY KEY(location_id, region_code)와 FK가 없는 구조입니다. 다른 테이블의 FK까지 모두 없앤 것은 아닙니다. 유효한 캠핑장을 참조하는지 별도 점검하는 부담이 생기며, 비파티션 비교본과 ID 타입·좌표 정밀도 등에도 차이가 있습니다.

02 / 요구사항과 모델링

개인: 요구사항·모델링 전 과정 참여 / 구축·산출물: 팀 공동

정보가 여러 사이트에 분산되고 출처별 형식이 달라 비교하기 어렵다는 문제에서 주제를 선정했습니다. 페르소나 2명을 설정하고 텐트 대여와 전기·Wi-Fi, 반려동물 동반과 주말 운영, 계곡 근처 여름 운영 캠핑장의 설명 검색을 쿼리 시나리오로 구체화했습니다. 업무기술서와 시나리오를 기준으로 모델의 범위를 조정했습니다.

CONCEPT → LOGICAL

초기 12개 엔터티

초기 HTML 설계안은 DataSource, Campsite, Location, Site, Glamping, Caravan, Operation, SanitaryFacility, SafetyFacility, Facility, NearbyFacility, Event를 검토했습니다.

다중값을 정리하고 업무 영역별 관계를 구체화했습니다. 이를 완전한 3정규형 달성으로 확대하지 않았으며, 장비 마스터는 검토안이고 최종 대여 정보는 장비별 플래그 방식입니다.

PHYSICAL / TEAM OUTPUT

최종 11개 테이블

실제 확보한 자료와 조회 시나리오에 맞춰 일부 영역을 통합하고 일정·대여·자연환경·지역 통계를 구체화했습니다.

초기 12개 엔터티와 최종 11개 테이블은 서로 다른 설계 단계입니다. 두 값을 합산하지 않습니다.

01

개념 설계 — 요구사항을 엔터티와 관계로 연결

캠핑장·위치·운영·시설·대여·검색통계를 중심으로 ER 다이어그램을 구성하고 MariaDB의 조건 조회와 MongoDB의 설명문 검색으로 역할을 나눴습니다.

02

논리 설계 — 다중값 분해와 업무 영역별 분리

전기·무선인터넷·장작판매처럼 한 칸에 있던 여러 값을 Y/N 속성으로 분해했습니다. 캠핑장 → 운영·시설 → 일정·사이트 유형·자연환경·부대시설·주변시설로 관계를 구체화했습니다. 최종 구성은 업무 테이블 10개와 통계 테이블 1개입니다.

03

물리 설계 — 타입·키·조회 조건 정의

컬럼별 타입·길이·NULL 허용·키를 정의하고 Y/N 속성은 CHAR(1)로 구성했습니다. 파티션 DDL의 좌표는 DECIMAL(10,4)이며, 비파티션 DDL에는 DECIMAL(15,10)이 남아 있습니다. 지역 코드·복합 PK·조회 조건 인덱스를 검토하되 실제 인덱스 선택 여부는 실행계획으로 구분했습니다.

BUILD & VALIDATION / TEAM

일반 DB와 파티션 DB 비교 환경

Rocky Linux 기반 VirtualBox VM에 MariaDB 10.11.15와 MongoDB를 구성했습니다. camping_db와 camping_db_part를 각각 구축하고 Python 스크립트로 DDL과 적재를 자동화했습니다.

EXPLAIN으로 접근 계획을, ANALYZE로 실행 통계를 비교했습니다. MongoDB에서는 텍스트 인덱스를 활용한 설명문 검색을 실험했습니다. 이 구축·검증은 팀 공동 작업입니다.

04 / 실행계획 해석과 점검

PLAN INTERPRETATION

ALL ≠ 프루닝 실패

ALL은 접근 대상 안에서의 스캔 방식입니다. partitions=p_daegu와 실제 57행을 함께 확인해 파티션 선택과 파티션 내부 접근을 나누어 해석했습니다.

POST-REVIEW / INDEX EXPERIMENT

후보와 실제 사용 구분

possible_keys에 인덱스가 보여도 실제 사용을 뜻하지 않습니다. 추가 인덱스 단계의 약 0.149ms는 대표 KPI에서 제외하고 실제 key·접근 방식 확인 과제로 남겼습니다.

PHYSICAL DESIGN

PK·FK 변경의 비용

위치 테이블의 복합 PK와 FK 제외는 DDL에서 확인한 설계입니다. 실제 오류 해결 로그는 없으므로 장애 해결 사례로 표현하지 않습니다. 고아 데이터와 지역 코드 검증이 후속으로 필요합니다.

TEAM SEARCH EXPERIMENT

빠른 검색과 같은 검색

검색 의미·대상 필드가 다르면 시간만 비교할 수 없습니다. 부분 문자열·단어 검색 요구를 구분하고 반환 ID 집합의 누락·추가 결과를 비교하는 것은 후속 과제입니다.

05 / 후속 개선 과제

사후 검토 항목 · 수정 완료 성과 아님
01

지역 코드로 통계 JOIN 통일

검증 노트의 문자열 지역명 대조에서 1,019행이 연결되지 않았습니다. 강원도 817, 전라북도 183, 세종 12, 결측 7행입니다. 개별 조회의 최종 누락 건수와는 다릅니다. 통계에도 공통 지역 코드를 적용하고 통계 부재와 검색 0건을 구분하는 것이 개선 방향입니다.

02

부모·자식 연결을 FK 기준으로 수정

일부 SQL의 부모 facility_id와 자식 PK를 연결하는 구문을, 자식의 facility_id 기준으로 수정해야 합니다. 우연히 같은 번호에 의존하지 않도록 서로 다른 PK를 가진 데이터로 재검증하는 작업이 남아 있습니다.

03

재현 가능한 적재와 반복 측정

입력 경로·컬렉션명·스키마를 통일하고 입력·성공·무시·실패 건수와 참조 무결성을 따로 검증해야 합니다. 동일 스키마·데이터·조건으로 반복 측정하고 접속 정보는 외부 설정으로 분리하는 것이 후속 방향입니다.

06 / 배운 점과 근거

조회 요구를 데이터 구조로 연결하고, 실행 시간뿐 아니라 파티션 선택·조인 순서·실제 행 수로 성능 변화를 설명하는 경험을 얻었습니다. 빠른 쿼리도 잘못된 조인이나 다른 검색 의미를 가질 수 있어 정확성과 무결성을 함께 검토했습니다.

  • 최종 발표자료 26~29장: 실행 통계 및 실행계획 원본 이미지
  • 최종 비파티션·파티션 DDL: 11개 테이블, 위치 테이블 제약, 18개 지역 파티션
  • 초기 개념도·HTML 설계안: 개념 모델과 초기 12개 엔터티
  • 제공된 포트폴리오·검증 노트: 데이터 대조, JOIN 점검, 후속 개선 항목

저장된 실습 산출물을 근거로 구성했습니다. 새 DB 실행·성능 재측정 결과가 아닙니다. 프로젝트 범위는 데이터베이스 설계·적재·조회 검증이며 회원·예약 서비스나 웹 운영 배포는 포함하지 않습니다.
