02 / 백업 → 장애 → 복원 → 검증

단일 멤버 장애와 과반수 상실을 구분해 시나리오를 구성했습니다. 백업 시점의 상태를 기준으로 복구 후 무엇이 남아야 하는지 먼저 정리하고, 제어 영역과 실행 중인 워크로드를 별도로 관찰했습니다.

01

실습 환경과 기준 상태 준비

VM별 호스트명·네트워크·machine-id를 정리하고 kubeadm으로 제어 노드를 조인했습니다. kubeconfig와 노드 IP를 확인한 뒤 노드 상태와 etcd Pod를 기준 화면으로 기록했습니다.

02

스냅샷과 비교할 리소스 정의

기록에서는 nginx·redis 테스트 리소스를 만든 뒤 etcd 스냅샷을 저장하고, 이후 apache·ConfigMap을 추가하는 순서로 시나리오를 구성했습니다. 복원 뒤 백업 시점 전후의 객체를 비교하도록 설계했습니다.

03

제어 프로세스와 etcd 장애 분리

kubelet을 중단해도 런타임의 etcd 컨테이너가 남을 수 있다는 점을 확인했습니다. Static Pod 매니페스트와 실제 컨테이너 상태를 함께 보며, 1멤버 장애와 2멤버 장애가 과반수에 미치는 차이를 추적했습니다.

04

복원 데이터와 멤버 구성 점검

기록의 스냅샷 복원 과정에서 데이터 디렉터리·노드 이름·peer 주소와 기존 멤버 상태를 점검했습니다. 복구 과정에 사용한 force-new-cluster 옵션은 일반 운영 절차와 구분하고, 멤버 동기화 문제를 별도 트러블슈팅으로 정리했습니다.

05

런타임 → etcd → 노드 순서로 확인

crictl로 etcd 실행 여부를 확인하고, etcd Pod와 노드 상태를 단계적으로 대조했습니다. 첨부 이미지에서는 etcd 3개 Running과 노드 6대 Ready를 확인할 수 있습니다. 백업 전후 테스트 객체의 최종 비교 출력은 추가 기록 과제로 남겼습니다.

복원 절차를 다시 정리하며 보완한 점

스냅샷 복원은 클러스터 멤버 식별 정보를 새로 구성하는 작업입니다. 한 멤버만 새롭게 복원한 뒤 기존 멤버의 파일을 되돌리는 것만으로 3멤버 재구성이 검증되는 것은 아닙니다. 새 클러스터의 멤버·peer 설정을 일치시키거나 올바른 멤버 재가입 절차를 적용하고, endpoint health/status와 member list를 확인하는 방향으로 복구 체크리스트를 보완했습니다.

etcd 스냅샷은 Kubernetes API 객체의 저장 상태를 복구하는 기준입니다. 애플리케이션의 PV 파일이나 외부 DB 데이터까지 함께 백업하는 것은 아니므로 데이터 백업 범위를 따로 설계해야 합니다.

03 / 오류에서 배운 복구의 경계

01 / STATIC POD

kubelet을 멈췄는데 etcd는 살아 있었다

문제 kubelet 서비스 중단과 etcd 컨테이너 종료를 같은 상태로 생각하면 장애 주입 결과를 잘못 해석할 수 있었습니다.

대응과 배운 점 매니페스트 경로와 crictl의 컨테이너 상태를 함께 확인했습니다. kubelet은 관리 주체, containerd는 실행 주체라는 계층을 구분하면서 실제 etcd 생존 상태를 기준으로 장애 범위를 판단했습니다.

02 / MEMBERSHIP

복원 뒤 learner 승격이 막혔다

문제 can only promote a learner member which is in sync with leader 메시지를 만나 멤버 복구가 단순 재시작으로 끝나지 않는다는 점을 확인했습니다.

대응과 배운 점 기록에서는 기존 멤버 상태를 점검하고 클러스터 재구성을 시도했습니다. 이 메시지 자체는 learner의 동기화 부족을 뜻하므로 기존 멤버 정보 충돌만으로 원인을 단정하지 않고, 동기화·통신·멤버십을 함께 보는 과제로 정리했습니다.

03 / JOIN & CONFIG

제어 노드인데 etcd가 없었다

문제 control-plane 조인 옵션 누락으로 워커로 합류하거나, 안정적인 controlPlaneEndpoint가 없어 추가 제어 노드 조인이 막혔습니다.

대응과 배운 점 실습용 복제 VM의 상태를 정리하고 --control-plane을 포함해 다시 조인했습니다. 공통 엔드포인트 설정을 확인하되, 특정 제어 노드 IP를 가리키는 설정만으로 API 고가용성이 완성되지는 않는다는 한계도 확인했습니다.

04 / CLIENT & NETWORK

클라이언트 주소와 노드 IP가 어긋났다

문제 kubectl의 로컬 8080 연결 거부와 VirtualBox NAT 주소가 INTERNAL-IP로 선택되는 문제를 각각 만났습니다.

대응과 배운 점 전자는 kubeconfig 위치·소유권, 후자는 kubelet의 node-ip 설정을 확인했습니다. 클라이언트 접속 문제와 노드 식별 문제를 분리해 해결 범위를 좁혔습니다.

05 / LEADER & LOGS

어느 리더의 로그를 봐야 할까?

문제 스케줄러 로그를 보려는 노드가 실제 리더인지 먼저 확인해야 했습니다. 제공 화면에는 scheduler Lease holder가 다른 제어 노드로 바뀌는 기록이 있습니다.

대응과 배운 점 Lease의 holderIdentity로 스케줄러 리더를 확인한 뒤 로그를 추적했습니다. etcd의 Raft 리더와 스케줄러 리더 선출은 별개이며, 후자는 API·etcd 가용성에 의존한다는 점을 구분했습니다.

06 / RESTORE VALIDATION

Running과 복구 완료는 다르다

문제 컨테이너가 Running이어도 노드가 NotReady일 수 있었습니다. 실제 중간 화면에서도 두 상태가 함께 나타납니다.

대응과 배운 점 런타임 실행, API 응답, 노드 Ready, etcd 멤버 건강 상태, 백업 시점의 객체를 서로 다른 검증 항목으로 나눴습니다. 다음 실습에서는 각 단계의 출력과 시간을 함께 남길 계획입니다.

실습 기록의 예외 처리와 운영 적용 구분

force-new-cluster는 기존 멤버가 살아 있으면 위험할 수 있어 공식 문서에서도 권장 복구 방식과 구분합니다. 이번 페이지에는 당시 사용 기록으로만 남겼으며 복사 실행하는 운영 절차로 제공하지 않습니다. Namespace의 finalizer 강제 제거 역시 원인을 조사한 뒤 판단할 예외 조치로 분리했습니다.

04 / 상태를 남기고, 결과를 대조하다

파일명보다 화면에 실제로 표시된 내용을 기준으로 캡션을 정리했습니다. 아래 이미지는 제공된 실행 기록이며, 서로 다른 시점의 화면을 복구 과정의 관찰 항목으로 묶었습니다.

구성·저장 데이터·리더 확인 화면 더 보기

스냅샷 저장·복원 명령의 전체 출력, endpoint health, 복구 전후 객체 대조와 RTO/RPO 측정값은 첨부 화면만으로 확인되지 않아 수치 성과로 제시하지 않았습니다.

05 / Pod가 실행되기까지

복구 과정을 이해하기 위해 요청 처리, 상태 저장, 배치, 실행을 나눠 정리했습니다. 아래는 학습 내용을 바탕으로 새로 구성한 개념 설명이며 실행 로그가 아닙니다.

  1. 요청과 API 처리

    kubectl 요청을 API 서버가 인증·인가·Admission 단계로 처리합니다.

  2. 원하는 상태 저장

    API 객체가 etcd에 저장됩니다. Deployment라면 컨트롤러가 ReplicaSet·Pod를 생성하도록 상태를 조정합니다.

  3. 스케줄링

    스케줄러가 미할당 Pod에 적합한 노드를 선택하고 API를 통해 배치 결과를 기록합니다.

  4. 실행

    해당 노드의 kubelet이 Pod 사양을 확인하고 CRI를 통해 containerd에 실행을 요청합니다.

  5. 상태 갱신

    kubelet이 실행 상태를 API 서버에 보고하고, 상태 변화가 저장·공유됩니다.

  6. 실습 관찰

    API·스케줄러 로그, etcd 키 조회와 watch, Pod·노드 상태를 각각 확인해 계층별 흐름을 대조합니다.

개념 참고: Kubernetes Static Pods · Scheduler · Leases. 공식 문서를 참고해 재구성한 설명용 흐름입니다.
