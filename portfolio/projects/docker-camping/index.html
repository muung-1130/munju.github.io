01 / 검사부터 병렬 배포까지

MY WORK / CI·CD

팀원이 코드를 올리면 검사·빌드·배포가 이어지는 흐름을 만들었습니다. 프론트와 백엔드를 독립된 작업으로 나누고, 공통 검사 이후 두 경로가 병렬로 진행되도록 구성했습니다.

01 / COMMONmain push → SonarQube Scanself-hosted runner · needs로 실행 순서 연결
BACKEND LANEBuild Backend → Harbor Push

build-backend → deploy-backend

커밋 SHA 이미지로 Swarm 서비스 갱신
FRONTEND LANEBuild Frontend → Harbor Push

build-frontend → deploy-frontend

커밋 SHA 이미지로 Swarm 서비스 갱신

Manager에 서로 다른 이름과 작업 폴더로 러너 2개를 구성해 두 빌드 작업을 처리하는 구조입니다.

01

실행 기반 — self-hosted runner 등록

내부 Harbor와 Swarm에 접근할 수 있는 Manager에 러너를 등록했습니다. 첫 번째 러너와 두 번째 러너의 설치 폴더·이름을 분리하고, 서비스로 등록해 재부팅 후에도 작업을 받을 수 있도록 구성했습니다.

02

검사와 인증 — 배포 전 공통 단계 정리

checkout으로 코드를 가져온 뒤 프론트·백엔드를 각각 SonarQube 프로젝트로 검사합니다. Harbor CA를 시스템과 Docker certs.d에 등록하고, GitHub Secrets로 인증 정보를 전달해 이미지 저장소에 로그인하도록 연결했습니다.

03

병렬 빌드 — 의존성과 실행 자원 함께 설계

build-backend와 build-frontend가 동일한 sonarqube 작업을 needs로 참조하도록 분리했습니다. 작업 두 개를 선언하는 것에 그치지 않고 러너를 두 개로 구성해 대기열을 나눴습니다. 각 작업은 자체 checkout과 빌드 경로를 갖고 SHA·latest 태그를 Harbor에 push합니다.

04

배포 — 서비스별 갱신과 롤백 경로 연결

각 deploy 작업은 자신의 빌드 작업이 완료되면 실행됩니다. SHA 태그로 배포 버전을 지정하고, --with-registry-auth로 이미지 인증을 전달했습니다. 한 번에 1개씩 10초 간격으로 갱신하고 실패 시 rollback하도록 설정해 배포 흐름에 복구 경로를 포함했습니다.

막혔던 지점과 해결 과정

01 / BUILD CONTEXT

로컬에서는 맞던 경로가 CI에서는 달랐다

문제 수동 작업 폴더와 러너의 checkout 경로를 혼용하면서 빌드 실행 위치를 여러 차례 조정했습니다.

정리 제출 워크플로는 working-directory를 ./backend와 ./frontend로 지정하고 빌드 컨텍스트를 .으로 통일했습니다.

배운 점 CI는 내 터미널의 현재 위치를 이어받지 않습니다. 저장소 기준 상대 경로로 실행 환경을 명확하게 만드는 습관을 얻었습니다.

02 / REGISTRY TRUST

레지스트리 주소뿐 아니라 신뢰 경로도 맞추기

문제 자체 서명 인증서를 사용하는 Harbor에서는 노드별 인증서 등록과 신뢰 설정이 필요했습니다.

해결 Manager와 Worker에 CA를 배포하고, 포트를 포함한 레지스트리 주소와 certs.d 경로를 맞췄습니다. 시스템 CA 등록도 함께 정리했습니다.

배운 점 이미지 경로·인증 정보·인증서 신뢰를 하나의 배포 준비 과정으로 관리해야 합니다.

03 / RUNNER LIFECYCLE

등록부터 상시 실행까지

문제 초기 러너 등록 실패와 Not configured 메시지를 확인했습니다. 수동 실행 상태만으로는 재부팅 후 작업 수신을 유지하기도 어려웠습니다.

해결 저장소 등록 설정을 다시 확인해 Runner successfully added 상태를 확인하고, svc.sh 서비스 등록·시작·상태 확인 순서로 실행 방식을 정리했습니다.

배운 점 한 번 실행하는 것과 지속적으로 운영하는 것은 서로 다른 설계 과제였습니다.

04 / PARALLEL JOBS

YAML을 나눠도 러너가 하나면 기다린다

문제 빌드 작업을 분리해도 러너가 1개이면 실제 실행은 순차로 처리됩니다.

해결 같은 Manager에 두 번째 러너를 별도 이름·폴더로 구성하고, 공통 검사 이후 두 빌드 경로를 처리하도록 연결했습니다.

배운 점 병렬화는 작업 의존성뿐 아니라 러너 수와 CPU·메모리 여유를 함께 설계하는 일입니다.

02 / 서비스와 인프라 구조

팀 공통 아키텍처

팀의 React 화면과 FastAPI 백엔드를 프론트·백엔드 각각 2개 replica로 구성한 제출 스택입니다. 데이터 계층은 MariaDB·MongoDB·Redis로 나누고, web-net과 내부 db-net으로 연결 범위를 구분했습니다. 관측 도구 구성은 팀 산출물로 소개합니다.

03 / 배포 이후의 운영까지

BACKUP · NETWORK · LOAD TEST

서비스를 올린 뒤에는 데이터를 보관하고, 통신 경계를 점검하고, 부하가 올라갈 때의 동작을 관찰했습니다. 반복되는 확인 과정을 스크립트와 실행 기록으로 남기는 데 집중했습니다.

01 / AUTOMATED BACKUP

두 데이터베이스의 백업 자동화

Worker3에서 docker exec로 MariaDB의 mysqldump와 MongoDB의 mongodump를 호출했습니다. MariaDB는 --single-transaction·--quick 옵션으로 SQL을 추출하고, MongoDB는 --archive --gzip으로 압축 보관합니다.

날짜·시간이 포함된 파일명으로 백업을 구분하고 crontab에 매일 05시 실행을 등록했습니다. 7일이 지난 파일을 정리하는 작업도 추가해 저장 공간을 관리했습니다.

운영 포인트 호스트에 별도로 도구를 설치하는 대신 DB 컨테이너 안의 도구를 사용해 실행 환경을 맞췄습니다.

02 / SLACK FEEDBACK

백업 결과를 관리자가 바로 확인하도록

MariaDB와 MongoDB 백업 명령이 차례로 완료되면 알림 스크립트가 실행되도록 연결했습니다. 최신 백업 파일 크기, 디스크 사용률과 남은 공간을 함께 전달하는 메시지를 구성했습니다.

Slack 응답 코드를 확인해 알림 완료·실패를 로그에 남겼습니다. 백업 파일만 만드는 흐름에서 상태를 확인할 수 있는 운영 흐름으로 확장했습니다.

03 / NETWORK BOUNDARY

웹과 데이터 계층의 통신 범위 분리

웹 트래픽은 web-net, 데이터 통신은 internal:true인 db-net으로 구분했습니다. 프론트·백엔드·DB의 연결 네트워크와 포트 구성을 확인하고 network inspect로 내부망 설정을 점검했습니다.

외부 DB 접근 시도와 내부 컨테이너 접속 확인 과정을 기록했습니다. HTTP 요청만으로 DB 통신을 판단하지 않고, DB 프로토콜·포트·클라이언트를 함께 확인해야 한다는 점을 배웠습니다.

04 / LOAD OBSERVATION

k6로 부하를 단계적으로 높이기

Smoke → Load → Stress → Spike 순서로 요청 패턴을 나눴습니다. 메인 통계·지역 통계·캠핑장 목록과 상세 API를 호출하며 실패율과 p95 응답 시간을 확인했습니다.

docker stats로 Backend·MariaDB·Redis 사용량을 함께 관찰하고, 응답 지연을 애플리케이션과 데이터 계층의 리소스 변화에 연결해 해석했습니다. 관찰한 메모리 사용량을 바탕으로 서비스별 reservations·limits 조정안을 정리했습니다.

Harbor·SonarQube·Actions를 설치하는 데서 끝내지 않고, 작업 의존성·이미지 버전·인증서·러너 실행 환경을 함께 정리했습니다. 실패한 지점에서 경로와 상태를 추적하며 배포를 하나의 흐름으로 보는 시각을 얻었습니다.
