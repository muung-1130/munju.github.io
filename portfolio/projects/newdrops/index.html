01 / 서비스가 배포되는 길을 만들다

Newdrops는 상품 탐색·판매 등록·포인트 구매를 제공하는 신발 거래 서비스입니다. 팀은 인증·상품·재고·주문과 Kafka 소비자를 분리해 쿠버네티스에 배치했습니다. 저는 인프라, CI/CD, Windows 기반 Harbor 설치를 맡아 개발 결과물이 클러스터까지 전달되는 경로를 구성했습니다.

MY ROLE

인프라 구성

노드·네임스페이스·서비스 연결 구조를 검토하고 CI/CD 도구의 실행 환경, 볼륨과 네트워크 경계를 정리했습니다.

MY FOCUS

Jenkins → Argo CD

빌드·분석·이미지 저장·매니페스트 변경을 파이프라인으로 연결하고, Jenkins 시연과 배포 흐름 설명을 담당했습니다.

MY BUILD

Windows Harbor

Docker Desktop과 WSL 2를 연결해 Harbor를 설치하고 권한·레지스트리 연결 문제를 단계별로 해결했습니다.

애플리케이션 개발, Kafka Saga, DB·관측 시스템은 팀 공통 산출물입니다. Jenkins 자료조사 예제와 최종 제출 코드는 구분해 정리했습니다.

02 / CI/CD — 변경을 배포 가능한 상태로

Build. Inspect. Publish. Sync.

Jenkins는 빌드와 산출물 이력을, Argo CD는 Git에 기록된 배포 상태의 동기화를 맡도록 역할을 나눴습니다.

01 / TRIGGER

코드 변경을 내부 CI로

GitHub Webhook을 ngrok 터널과 Jenkins NodePort로 전달하는 구조입니다. checkout scm으로 소스를 받고 disableConcurrentBuilds()로 겹치는 실행을 제어합니다.

02 / QUALITY

분석 서버가 준비된 뒤 검사

SonarQube 상태가 UP인지 10초 간격으로 최대 30회 확인합니다. 준비 후 Scanner를 실행하고 Webhook 콜백으로 Quality Gate 결과를 받도록 연결했습니다.

03 / IMAGE

빌드 번호로 이미지 추적

인증·상품·재고·주문·프론트엔드와 결제·주문·환불 소비자, 총 8개 이미지를 순차 빌드·Push합니다. Harbor의 프로젝트와 BUILD_NUMBER 태그로 빌드와 이미지를 연결합니다.

04 / SCAN

이미지의 취약점을 확인

주요 5개 서비스 이미지에 HIGH·CRITICAL 검사를 수행하고 Trivy DB 캐시를 재사용합니다. 제출 버전은 결과 확인 중심이며, 품질·취약점 결과에 따른 배포 차단은 보완 과제로 남겼습니다.

05 / GITOPS

Git에 배포할 버전을 기록

배포 매니페스트의 이미지 태그를 갱신하고 Git에 커밋합니다. Argo CD는 Git 변경을 감지해 Kubernetes에 동기화합니다. 자체 태그 갱신 커밋은 다시 Update Manifest를 실행하지 않도록 조건을 둡니다.

06 / BACKUP

이미지와 소스 이력을 함께 보관

이미지는 Harbor에, 빌드 시점 소스는 git archive로 묶어 MinIO에 저장합니다. 빌드 번호·브랜치·커밋을 파일명에 포함해 추적할 수 있도록 구성했습니다.

제출 원본 CI/CD draw.io ↓
파이프라인 구현 범위와 다음 개선

최종본은 서비스별 순차 빌드입니다. 자료조사 노트의 변경 감지·parallel 예제를 실제 적용 완료로 혼동하지 않았습니다. Quality Gate는 abortPipeline: false, Trivy는 exit-code 0 및 오류 허용 설정입니다. 이후 변경 서비스만 빌드하는 병렬 구성, 소비자를 포함한 검사 범위 확대, 정책 기반 차단과 배포 후 상태 검증을 보완할 계획입니다.

자체 커밋 조건은 Update Manifest 단계에만 적용되어 후속 파이프라인 전체 실행을 막지는 않습니다. 트리거 단계의 필터링까지 확장하면 불필요한 재빌드를 줄일 수 있습니다.

03 / 문제 해결 — 도구 사이의 경계를 따라

01 / WINDOWS × WSL

Docker는 켜졌는데 설치가 안 됐다

증상 Windows와 WSL 사이에서 Docker 엔진을 사용할 수 없거나 API 접근이 거부됐습니다.
대응 WSL 2 엔진과 Ubuntu Integration을 확인하고, Linux 계정의 Docker 그룹 및 세션 반영 상태를 점검했습니다.
배운 점 설치 파일보다 실행 환경과 권한 경계를 먼저 확인해야 했습니다.

02 / CREDENTIAL HELPER

공개 이미지 Pull에서도 인증 오류

증상 SonarQube 이미지를 받는 과정에서 WSL과 Docker Desktop 사이의 자격증명 헬퍼 오류가 발생했습니다.
대응 사용자 Docker 설정의 헬퍼 구성을 확인하고 실습 환경에서 설정을 정리해 다시 실행했습니다.
보완 운영 환경에서는 정상적인 헬퍼·인증 저장소 연결을 유지하도록 절차를 정리합니다.

03 / CALLBACK

Quality Gate가 PENDING에 머무는 경로

점검 분석 요청 성공과 결과 콜백 성공은 다른 통신 경로였습니다.
대응 SonarQube → Jenkins :8080 콜백을 기준으로 송신·수신 NetworkPolicy와 Webhook 주소를 함께 점검하는 절차를 정리했습니다.
배운 점 비동기 연동은 요청뿐 아니라 돌아오는 경로까지 확인해야 합니다.

04 / PERSISTENCE

재시작 후 Scanner 설정이 사라졌다

기록 6월 작업 기록에 Jenkins 재시작 후 SonarQube Scanner 설정 유실 문제가 남아 있습니다.
분석 도구 경로와 설정 저장을 확인하고 SCM 기반 Pipeline 및 JCasC로 설정을 고정하는 방향을 정리했습니다.
보완 제출 기록에서 JCasC 적용은 후속 과제이므로 완료 성과와 구분합니다.

05 / REGISTRY

설치 성공과 다른 PC의 접속은 달랐다

점검 Harbor hostname·HTTP/HTTPS·인증서 경로와 클라이언트 레지스트리 설정을 함께 맞췄습니다.
대응 관리 화면 접속과 클라이언트 login·push·pull 경로를 나눠 확인하는 과정을 기록했습니다.
보완 실습의 자체 서명·HTTP 설정을 운영 기준으로 확대하지 않고 신뢰 체인과 TLS 정책을 보완합니다.

06 / DECLARATIVE DEPLOY

수동 변경보다 Git의 상태가 우선했다

점검 Argo CD selfHeal 환경에서는 수동 이미지 변경이 Git 상태로 되돌아갈 수 있습니다.
대응 시연 문서에서 롤링 업데이트·롤백 경로를 정리하고 Git에 기록된 버전을 중심으로 배포를 설명했습니다.
보완 Git revert와 동기화 정책을 포함한 복구 절차를 표준화합니다.

04 / 인프라와 Windows Harbor 구축

제출 인프라 설계는 Control Plane 1대와 Worker 4대로 구성됩니다. CI/CD, 공개 서비스, 업무 서비스, 데이터베이스와 모니터링을 네임스페이스로 구분하고 노드의 자원과 데이터 저장 위치를 함께 고려했습니다.

CLUSTER

서비스·도구의 책임 분리

Jenkins와 SonarQube의 실행 위치 및 PVC, 앱 서비스와 데이터 저장소의 배치를 구분했습니다. NetworkPolicy로 DNS·분석 콜백·레지스트리·백업 통신 경로를 정리하는 데 중점을 뒀습니다.

WINDOWS HOST

WSL 2 위에 Linux 레지스트리

Docker Desktop 준비 → WSL 통합 → Harbor 설정 → 설치 → 웹 접근 및 클라이언트 연결 점검 순으로 진행했습니다. Windows는 호스트이며 Harbor는 Linux 컨테이너로 실행하는 구조입니다.

개인 PC의 설치 실습 기록과 팀 최종 Harbor 운영 위치는 구분했습니다. 단일 Control Plane과 local-path 저장소를 사용한 실습 구성으로, 고가용성 운영을 완료한 사례로 표현하지 않습니다.

05 / 서비스 화면 — 팀이 만든 사용자 경험
