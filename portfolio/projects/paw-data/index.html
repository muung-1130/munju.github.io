01 / 어디에 살고, 어디서 무엇을 시작할까?

Paw-Data의 출발점은 반려동물을 기르는 사람의 거주지 선택과 반려동물 관련 업종의 창업 의사결정입니다. “어디에 살면 좋을까?”, “어느 지역이 경쟁이 치열하거나 기회가 있을까?”, “어떤 업종을 선택하면 좋을까?”라는 세 질문을 데이터로 탐색하도록 기획했습니다.

01 / LIVING

보호자를 위한
거주지 추천

의료·놀이문화·돌봄교육·미용위생의 중요도를 직접 조절하고, 서울 25개 자치구의 지도와 추천 순위를 함께 살펴보도록 구성했습니다.

02 / LOCATION

레드오션과 블루오션의
후보 지역 탐색

선택한 업종의 시설 분포와 반려동물 등록 수를 비교해 공급이 밀집한 지역과 상대적으로 공급이 적은 지역을 살펴봅니다. 최대 3개 자치구를 비교하며 상권 후보를 좁히는 것이 목적입니다.

03 / MARKET

어떤 업종을 선택할지
시장 분석

식품·미용위생·서비스·일반용품·의료건강의 키워드 규모와 성장률, 과거 검색 추이를 비교해 관심 업종과 추가 조사 대상을 선택하도록 기획했습니다.

레드오션·블루오션은 서비스의 탐색 목적입니다. 시설 수는 공급, 등록 수는 잠재 수요를 살펴보는 참고 지표이며 실제 매출·상권 경쟁도·창업 성공을 확정하는 판정 모델은 아닙니다.

02 / 화면으로 보는 작업

ORIGINAL REACT / DEMO DATA

GitHub의 React 소스를 로컬에서 실행해 기록한 화면입니다. 운영 DB 연결 없이 원본 코드에 내장된 예시 데이터를 사용했습니다. 캡처용으로 라벨·높이를 정리하고 로컬 자치구 경계를 적용했으며, 상권 위험도 판정은 생략했습니다. 추천 점수·상권 수치·검색 차트는 화면 동작을 보여주는 예시이며 실제 지역 통계나 시장 성과로 해석하지 않습니다.

03 / 자료부터 화면까지, 제가 맡은 연결

DATA · DATABASE · FRONTEND · INTEGRATION

React 개발을 주로 맡으면서 자료 조사, 정형데이터 정규화와 DB 구축 과정에도 참여했습니다. 팀원과 데이터 구조를 함께 맞추고, DB의 조회 결과가 API를 거쳐 화면에 정확히 표시되는 지점까지 연결했습니다.

01

주제 구체화와 사용할 자료 찾기

반려동물 보호자와 예비 창업자의 질문을 거주지·상권·시장 분석의 세 화면으로 구체화했습니다. 반려동물 동반 시설, 지역별 등록 개체 수, 지역 면적, 서울시 점포·상권 자료와 네이버 키워드 자료를 조사하고, 지역 단위·분류·제공 항목이 서비스 목적에 맞는지 살펴봤습니다. 화면 설계와 기능명세서 작성, 중간 발표에도 참여했습니다.

02

정형데이터 정규화와 공통 지역 기준 정리

시설·주소·행정구역·업종 분류·등록 현황을 분리하고 참조 키로 연결하는 정규화 설계에 참여했습니다. 특히 서울시 상권 자료를 같은 자치구 기준으로 비교할 수 있도록 지역 코드와 컬럼 의미를 확인하고, 점포 데이터 정규화 및 DB 적재 과정에 참여했습니다.

03

DB 구축 참여와 화면에 필요한 조회값 확인

팀의 MariaDB 모델·적재 작업에 참여하며 시설 수와 등록 수를 자치구 단위로 조회하는 구조를 함께 확인했습니다. Workbench의 SQL 조회값과 대시보드 수치를 대조해 데이터 연결의 기준값을 잡았습니다. MongoDB의 좌표·운영 설명과 관계형 시설 데이터를 연결하는 팀 구조를 이해하고, 화면에서는 API가 반환한 시설 위치와 상세 정보를 사용했습니다.

04

React 화면과 FastAPI 연결

프론트엔드의 API 기준 주소를 REACT_APP_API_URL로 관리하고, 추천 요청·자치구별 시설 조회·상권 대시보드 응답을 화면 상태에 연결했습니다. /api/dashboard 응답을 자치구 이름으로 매핑해 차트 입력으로 전달하고, DB → API → 브라우저 요청 → React 상태 → 렌더링 순서로 값의 흐름을 점검했습니다.

05

지도와 비교 차트의 선택 상태 동기화

가중치 입력·적용 상태, 추천 순위, GeoJSON 지도 선택과 이동을 연결했습니다. selectedGus 하나로 최대 3개 지역의 선택 칩·지도·Chart.js 차트를 갱신하고, useRef로 인스턴스를 관리해 update()와 destroy()를 구분했습니다. 시설 수와 등록 개체 수는 좌·우 축으로 나눴습니다.

06

업종 탐색을 위한 시장 시각화

세 번째 탭에 시장 분석 화면을 구성하고 Recharts의 도넛·트리맵·막대·라인 차트와 wordcloud를 활용했습니다. 분야의 규모, 변화율, 과거 추이를 다른 시각화로 구분해 업종 선택의 근거를 살펴보도록 했습니다. 현재 저장소의 시장 차트는 내장 예시값을 사용하므로 실시간 시장 API 연동 완료로 표현하지 않습니다.

정규화·데이터베이스 참여 내용을 더 자세히

행정구역: sido → sigungu → address로 연결하고, registration과 area는 sigungu를 참조하는 구조입니다. 주소·등록·면적마다 시도 식별자를 반복 보유하는 대신 시군구 관계로 상위 지역을 찾도록 설계했습니다.

시설과 분류: facility는 address_id와 category_sub_id를 사용합니다. 소분류가 category_main을 참조하게 해 시설 행에 대분류를 중복 기록할 때 생기는 분류 불일치를 줄이는 방향으로 정리했습니다.

상권 자료: 점포 데이터를 분기·자치구·업종 단위로 구분하고, (분기코드, 시군구 ID, 업종코드)를 복합 식별 기준으로 삼는 팀 설계와 적재 과정에 참여했습니다. 자료의 컬럼명만 믿지 않고 코드 값의 실제 지역 단위를 확인했습니다.

연결 검증: 프론트 수치와 SQL 집계를 비교하며 시설 ‘개’, 등록 ‘마리’, 지역별 합계와 예시 동 평균을 구분했습니다. 정규화 참여를 설명하되 모든 함수 종속성·DDL 제약을 재검증한 BCNF 인증처럼 표현하지 않습니다.

04 / 데이터와 화면 사이의 문제를 풀다

작업 기록에서 반복된 질문은 “데이터가 없는가, 연결이 안 되는가, 표현이 잘못됐는가?”였습니다. 문제가 나타난 화면에서 출발해 원천 자료와 DB, API, 상태와 스타일로 범위를 나누어 확인했습니다.

13 → 251

강남구 의료시설 · fallback 예시값에서 DB 조회값으로 연결

본인 제공 작업 기록의 전후 수치. 현재 코드의 환경변수 API 주소 적용은 확인했으며, 당시 실서버 251건은 이번 로컬 시연에서 재조회하지 않았습니다.
01 / DATA AVAILABILITY

필요한 업종 매출 자료가 없었다

문제 동물병원 매출로 입지를 비교하려 했지만 당시 확인한 상권 자료의 제공 업종에 포함되지 않았습니다.

대응 확보 가능한 시설 위치·분류별 시설 수와 반려동물 등록 수를 비교하는 방향으로 분석을 조정했습니다. 시설 공급과 잠재 수요를 함께 보여주어 후보 지역을 탐색하도록 했습니다.

배운 점 기획을 데이터에 억지로 맞추기보다 자료의 범위와 한계를 먼저 확인해야 했습니다.

02 / REGION CODE

컬럼명과 실제 지역 단위가 달랐다

문제 소득·소비 자료의 행정동_코드라는 이름과 실제 자치구 단위 값이 맞지 않았습니다.

대응 작업 기록에서 25개 자치구 코드와 값을 대조한 뒤 지역 단위를 정정하고, 점포 자료와 비교할 수 있는 기준으로 정규화했습니다.

배운 점 컬럼 이름뿐 아니라 값의 집합과 조인 기준을 검증해야 데이터가 다른 지역에 잘못 연결되지 않습니다.

03 / API CONNECTION

정상 화면 뒤에 숨어 있던 더미 값

문제 SQL 조회는 251개인데 차트는 13을 표시했습니다. 13이 예시 동 평균과 같다는 점에서 fallback 경로를 의심했고, Network의 연결 시간 초과와 다른 PC의 하드코딩 주소를 확인했습니다.

해결 API 주소를 REACT_APP_API_URL로 분리하고 개발 서버를 재시작했습니다. /api/dashboard 직접 응답 → 자치구 키 매핑 → 차트 입력을 차례로 확인하고 콘솔에서 API·fallback 출처를 구분했습니다.

배운 점 fallback은 빈 화면을 막지만 연결 오류를 감출 수 있어, 데이터 상태를 사용자에게도 보여주는 보완이 필요합니다.

04 / CHART SCALE

실데이터를 받자 막대가 잘렸다

문제 예시값에 맞춘 y축 최대값 20 때문에 실제 시설 수 251을 제대로 표현하지 못했습니다.

해결 고정 최대값을 제거해 자동 스케일을 적용하고, 시설 수와 반려동물 등록 수를 좌·우 이중 축으로 분리했습니다. 현재 코드에서도 분리된 축 설정을 확인할 수 있습니다.

배운 점 데이터 연결 검증은 응답 성공뿐 아니라 실제 값의 범위와 단위로 화면을 확인하는 과정까지 포함합니다.

05 / GEOJSON DELIVERY

지도 경계를 읽지 못한 문제

문제 백엔드 경로에서 경계 파일을 요청하며 JSON이 아닌 응답을 받아 Invalid GeoJSON object 오류가 발생했습니다.

해결 경계 파일을 React public 폴더의 정적 리소스로 배치하고 /seoul_gu.geojson으로 불러오도록 정리했습니다. 이미지도 public의 경로를 기준으로 맞췄습니다.

배운 점 정적 에셋 전달과 동적 API 요청의 책임을 나누면 경로 문제를 더 쉽게 추적할 수 있습니다.

06 / LEAFLET STYLE

툴팁에 남아 있던 기본 테두리

문제 커스텀 스타일을 넣어도 Leaflet 툴팁의 흰 배경·테두리·화살표가 남았습니다.

해결 .leaflet-tooltip.custom-tooltip으로 선택자 명시도를 높이고 ::before 화살표를 별도로 제어했습니다. 현재 코드에서 해당 선택자와 화살표 제거를 확인했습니다.

배운 점 외부 UI 라이브러리는 컴포넌트뿐 아니라 기본 CSS와 가상 요소까지 함께 점검해야 했습니다.

발생 당시의 상황·해결 과정은 제공 작업 기록을 기준으로 정리했습니다. 현재 저장소 코드 대조와 실서버의 당시 결과는 구분합니다.

추가 UI 점검 기록

지도 클릭 테두리는 GeoJSON 경계와 브라우저 포커스를, 강아지 이미지 배경은 컨테이너 CSS와 원본 픽셀을 나누어 점검했습니다. 폰트는 선언·실제 로딩·폴백을 구분했습니다. 이 항목은 점검 경험이며 모든 최종 수정이 검증된 실적으로 확대하지 않습니다.

05 / 팀의 데이터 위에, 사용자 경험을

React김문주 · 화면·상태·시각화
→
Python / FastAPI장우성 · 백엔드 API
→
MariaDB + MongoDB박영서 · DB·문서화 주 담당
김문주 · 정규화·DB 구축 참여

관계형 DB의 시설·주소·분류·등록 현황과 MongoDB의 좌표·운영 설명을 API 계층에서 연결하는 팀 설계입니다. 프론트엔드는 DB에 직접 접근하지 않고 API 응답을 지도와 차트에 사용합니다. 백엔드·DB 주 담당자의 작업과 협업하면서 저는 자료 조사·정규화·DB 구축에도 참여하고, 프론트와 백엔드의 응답 연결 및 화면 검증을 담당했습니다.

APPLICATION / VM 1

화면과 API의 연결

React(3000)와 FastAPI(8000)를 앱 서버에 배치한 구성입니다. 저는 프론트엔드의 API 주소와 응답 구조를 맞추고, 데이터가 지도·추천 카드·차트에 반영되는 흐름을 검증했습니다.

DATABASE / VM 2 · VM 3

정형·비정형 데이터의 분리

08 / 기술 부록 & 작업 범위

추천과 비교의 구현 메모

추천은 Σ(항목 점수 × 가중치) ÷ Σ가중치입니다. 원본 BASE_DATA의 강남구는 모두 3이면 86점, 의료 5·나머지 1이면 92점으로 반올림됩니다. 이 값은 예시 입력의 계산 결과입니다. 모든 가중치가 0이면 미설정 안내를 제공하고, 유효한 0점은 결측 기본값과 구분하는 방향으로 개선해야 합니다.

추천 지도 시설 마커와 상권 버블은 다릅니다. 전자는 API의 시설 좌표, 후자는 지역 중심점에 범주별 간격을 더한 통계 표현입니다. GeoJSON의 [경도, 위도]와 Leaflet의 [위도, 경도]도 변환 경계에서 구분해야 합니다.
